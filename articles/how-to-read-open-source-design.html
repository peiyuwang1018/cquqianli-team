新人第一次打开一台完整机器人的 CAD，经常会出现两种截然不同的感觉。

一种是：

“东西好多，我完全不知道从哪里开始看。”

另一种是：

“好像也没什么难的。这个是轴承，这个是电机，这里是同步轮，这块是 CNC。”

后者有时候反而更加危险。

因为认识一个零件叫什么，并不意味着看懂了一个设计。

你当然可以把整台机器人的所有零件名称都背下来。但如果继续往下问：

  • 为什么这个电机放在这里，而不是直接放在旋转中心？
  • 为什么这里还需要一级传动？
  • 为什么用了这个规格的轴承？
  • 为什么主体是一整块 CNC，而不是几块板件拼起来？
  • 为什么这两个模块必须一起考虑，而另外两个模块却可以各画各的？
  • 如果轴承直径增加 20%，哪些结构必须跟着变化？

这时候，真正的设计知识才开始出现。

所以这篇真正想讨论的并不是：

怎么快速看懂一个 CAD。

而是：

怎么从别人已经完成的结构里，把设计者当时做过的判断重新读出来。

换句话说：

不要只看 Geometry，要读 Geometry 背后的 Design Decisions

01为什么要看开源？——先给脑子里装一点“墨水”

我一直很喜欢把学习机械设计类比成学习写文章。

如果一个人几乎没有认真读过任何优秀作品，却要求他：

“现在不要模仿任何人，完全原创地写一篇好文章。”

当然不是绝对不可能。

但除非是极少数天才，对于大多数人来说都非常困难。

原因其实很简单：

肚子里没有墨水。

阅读经典作品的目的，并不是以后把经典作品原封不动抄一遍。

真正逐渐积累的是：

  • 词汇；
  • 句式；
  • 篇章结构；
  • 表达方式；
  • 审美；
  • 对“什么叫好”的判断。

机械也是一样。

看优秀开源，真正应该留下来的，并不是：

“某队某年的 J0 轴长这个样子。”

而是：

  • 一个旋转自由度通常可以怎样实现；
  • 电机可以怎样布置；
  • 传动可以承担哪些功能；
  • 轴承和轴系通常怎样组织；
  • 模块之间怎样定义接口；
  • 怎样处理走线、装配、防护和维护；
  • 哪些结构已经在真实比赛工况里被验证过。

这些东西最终会逐渐形成自己的：

机械词汇 + 机械句式 + 机械范式

所以从这个角度看：

优秀开源不是答案库，而是机械设计语言的语料库。

机械领域也有自己的“公式”

除了“读经典”这个比喻，我还喜欢把成熟的机械设计范式理解成：

机械设计里的公式。

假设一个完全没有机械经验的人第一次遇到这样的问题：

“这里需要一根能够旋转、同时承受一定载荷的轴。”

如果脑子里没有任何成熟范式，那么搜索空间几乎是无限的。

但当你看过足够多成熟轴系以后，问题会开始自动被拆成：

原本一个完全开放的问题，被成熟工程经验迅速压缩到了几个合理候选。

这和做数学题非常像：

识别题型 → 找到公式 → 检查适用条件 → 使用公式

所以我并不排斥“套公式”这个说法。

事实上：

对于新人，能够正确地套一个成熟公式，本来就是非常重要的能力。

问题从来不是“为什么要套公式”，而是：

你到底会不会套。

真正死记硬背的状态是：

而合理的移植应该是：

因此更准确地说：

范式 + 适用条件判断 + 当前约束修正 = 真正的“套公式”

不要为了证明自己而拒绝成熟答案

新人有时候会把：

“这个结构参考了别人。”

理解成：

“那我就没有创新。”

于是产生一种很危险的好高骛远：

“我要自己从零做一个以前从来没有人做过的东西。”

我觉得完全没有必要。

真正从底层创造一种新的机械范式，本来就是极少、极难，也极珍贵的事情。

绝大多数日常工程设计更常见的状态其实是：

成熟范式 A + 成熟范式 B + 当前特殊约束 → 一个新的具体设计

例如：

  • 把一个成熟传动重新布置到新的空间；
  • 把两种已有结构融合起来；
  • 把成熟模块压缩进更小包络；
  • 改变驱动位置以降低惯量；
  • 重新组织模块接口；
  • 把成熟方案适配到新的比赛功能。

这些完全可以是有价值的创新。

工程不是创意比赛。

所以：

创新不是目的，解决问题才是目的

如果成熟方案已经能够稳定解决问题：

用它。

如果不完全适合：

修改、移植、化用、组合。

如果现有范式已经真正成为系统瓶颈：

再进入更高风险的自主探索。

确定范式与非确定范式：有些地方有路，有些地方只有指南针

我以前喜欢用一个比喻区分不同类型的设计问题。

有些问题像：

一条已经修好的道路。

道路不一定只有一条，到了路口也可能有多个方向，但通常已经有路牌告诉你有哪些选择。

例如大量成熟的：

  • 轴系；
  • 传动；
  • 定位；
  • 紧固；
  • 标准件应用；

都已经存在比较明确的设计范式。

我把这类问题理解成：

确定范式较强的问题。

这里的“确定”不是说只有一个正确答案，而是：

成熟工程经验已经把巨大的搜索空间压缩到了少数几个合理方向。

另一类问题则更像：

站在一片茫茫沙漠里。

没有现成道路。

只知道终点大概在哪，手里只有一只指南针。

例如：

  • 新规则第一次出现的新任务；
  • 没有成熟先例的机构拓扑；
  • 多个模块高度耦合的问题；
  • 已有成熟范式都无法满足的特殊性能要求。

这时候就需要：

这属于更加：

非确定范式的探索。

当然，现实并不是简单的二分类。

它更像一条连续谱：

一个人的工程经验越来越多以后，经常会出现一个很有意思的变化：

以前觉得是一片“沙漠”的问题，后来发现只是几个自己已经见过的问题重新组合。

这就是看开源真正开始产生复利的地方。

02第一遍：先认全，再找功能骨架

有了上面的观念以后，我们终于可以真正打开一套开源。

面对一个几百甚至几千零件的 CAD，第一件不应该做的事情是：

立刻钻进某一个小零件里研究圆角和减重孔。

先把机器看清楚。

先看它到底在干什么

如果开源提供：

  • 设计文档；
  • 技术报告；
  • 演示视频；
  • 比赛录像；
  • 动画；

先看这些。

CAD 主要告诉你：

“它长什么样。”

而视频和文档会告诉你：

“它为什么存在，以及它到底怎么工作。”

尤其对于：

  • 轮腿；
  • 发射；
  • 机械臂；
  • 变形机构；

如果连实际动作都没有看过，仅靠静态模型非常容易误判功能。

再进入 CAD，把复杂结构拆开

进入 Fusion 或其他 CAD 后，先使用最基本的观察工具：

  • Hide / Show；
  • Isolate；
  • Section View；
  • Joint；
  • Rigid Group；
  • Fix；
  • 必要时逐层隐藏模块。

这些工具的目的不是让你立即开始复刻，而是帮助你回答：

这里到底有哪些东西？

所以最基础的阅读顺序其实是：

先认全 → 再理解功能 → 最后才开始抽象

如果连：

  • 这个零件叫什么；
  • 属于哪个模块；
  • 起什么作用；

都还不知道，就暂时不要急着讨论：

“这个是不是核心？”

“核心 / 外围”不是“重要 / 不重要”

以前有人问我：

对一台完整机器人，怎么快速判断哪些是核心模块，哪些是次要部分？

这个问题本身没有错，但很容易被误解。

例如对一个腿模块来说，气弹簧、限位件、防护件可能并不决定最基本的运动拓扑。

于是从“先理解这个腿怎么运动”的视角，可以暂时把它们放到外围。

但这绝不意味着：

它们不重要。

气弹簧可能影响：

  • 重力补偿；
  • 功耗；
  • 弹跳能力。

限位可能决定：

  • 冲击保护；
  • 运动范围；
  • 复位一致性。

防护甚至可能决定：

这个机构能不能活过比赛。

所以：

核心 / 外围是一种分析工具，不是一张重要性排行榜

所谓核心，只是在当前分析层级下：

先抓住决定主要功能和结构关系的骨架。

分析层级改变以后，所谓“核心”也会改变。

第一遍真正要找的是“功能骨架”

看复杂机械结构时，不要一开始按“零件清单”思考。

先试着把整个模块压缩成一条功能链：

以前分析工程机器人 J0 轴时，我基本就是沿着这样的路径看。

功能

这个模块要做什么？

有几个自由度？

例如：

J0 需要实现一个 360° 旋转自由度。

驱动

用什么：

  • 电机；
  • 气缸；
  • 其他执行器？

为什么：

  • 力矩够？
  • 速度够？

真正理解电机选型，至少应该能够回答：

当前任务为什么需要这个数量级的输出？

驱动位置

为什么电机放在这里？

位置很多时候并不是随便排布的。

可能是为了：

  • 留出中空过线；
  • 放滑环；
  • 避让其他机构；
  • 做配重；
  • 降低某段运动惯量；
  • 满足整机包络。

传动

为什么这里不是直驱，而用了：

  • 同步带；
  • 链；
  • 齿轮；
  • 减速器？

传动并不只是：

“把运动传过去。”

它同时可能承担：

  • 减速；
  • 增扭；
  • 改变执行器位置；
  • 远置驱动；
  • 留中空空间；
  • 重新组织整机布局。

轴系 / 运动副

如果是旋转：

  • 用什么轴承？
  • 谁转？
  • 谁固定？
  • 轴承承受什么载荷？
  • 怎样进行轴向和径向定位？

如果是平移：

  • 线轨？
  • 滚轮？
  • 滑块？
  • 其他导向？

主体结构

谁把这些功能元件连接起来？

主体结构需要进一步考虑：

  • 力从哪里经过；
  • 主要受拉、压、弯还是扭；
  • 哪里需要强度；
  • 哪里需要刚度；
  • 为什么采用这种结构形式。

电气

最后还不能忘记：

  • 滑环；
  • 线束；
  • 控制板；
  • 传感器；
  • 接头；
  • 运动线缆。

真实机器人不存在一个：

“机械画完以后，电控自己会找到空间。”

的阶段。

03第二遍：从“看形状”到“看关系”——开源阅读四问

第一遍看完以后，我们已经知道：

这个模块是什么，以及大概怎么工作。

但这仍然只是“看懂功能”。

真正开始读设计，需要继续追问：

为什么最后是这样？

我以前把这件事总结成三个问题。

现在我更愿意把它正式整理成四问。

Q1｜Why does it exist? · 它为什么存在？

看到一个零件、孔、台阶、凸台或者局部特征时，先问：

它到底解决了什么问题？

可能是：

  • 承载；
  • 定位；
  • 紧固；
  • 防护；
  • 走线；
  • 限位；
  • 调节；
  • 散热；
  • 维护；
  • 加工。

如果完全说不清：

“为什么这里一定需要它？”

那么目前大概率还停留在：

“我知道这里有一个东西。”

而不是：

“我知道为什么要有它。”

Q2｜How is it related? · 它和谁发生关系？

机械零件几乎永远不是孤立存在的。

继续问：

  • 它和谁接触？
  • 谁驱动谁？
  • 谁支撑谁？
  • 力从哪里传到哪里？
  • 谁给谁定位？
  • 怎样紧固？
  • 怎样装进去？
  • 怎样拆下来？
  • 哪些尺寸由旁边零件决定？

真正需要看到的是：

Relationship

而不只是：

Shape

例如看到一个轴承，不应该只记住：

“这里装了一个轴承。”

而应该继续追：

  • 内圈装在谁上？
  • 外圈装在谁里？
  • 内圈两侧怎么限位？
  • 外圈两侧怎么限位？
  • 载荷最终从哪里传到哪里？

这时候一个轴承才真正开始变成“设计”。

Q3｜Why this implementation? · 为什么最后是这样实现？

继续追问：

  • 为什么是这个形状？
  • 为什么是这个尺寸？
  • 为什么是这个材料？
  • 为什么用这个标准件？
  • 为什么采用这个加工方法？
  • 为什么这里是一体件，而不是组合件？
  • 为什么这里有一个台阶？
  • 为什么这个位置必须留空间？
  • 为什么这个结构看起来比理论最小方案复杂？

这一步开始真正进入：

设计取舍。

一个结构最终长成什么样，往往同时受到：

  • 功能；
  • 载荷；
  • 空间；
  • 标准件；
  • 加工；
  • 装配；
  • 走线；
  • 维护；
  • 成本；

共同决定。

Q4｜What changes if constraints change? · 如果关键条件变化，它会怎么变？

这是我现在认为非常重要的第四问。

例如主动改变一个条件：

  • 电机换型号；
  • 轴承直径增加 20%；
  • 负载翻倍；
  • 整体宽度减少 20%；
  • 质量预算下降；
  • 需要加入快拆；
  • CNC 改成板件组合；
  • 接口位置发生变化。

然后问：

整个设计哪里必须跟着变化？

如果一个人能够完整复刻一个模块，却完全无法回答这个问题，那么：

他可能记住了答案，但还没有真正学会这道题。

所以这第四问，其实是在测试：

你记住的是 Geometry，还是理解了 Design Logic？

04第三遍：从最终结构反推设计因果——耦合、主次与设计顺序

到这里，我们已经能够解释很多单个结构：

为什么存在，为什么这样做。

但看整机或者复杂模块时，还需要再向上抽象一层。

因为真正的设计从来不是：

一堆互相独立的零件分别画完，再随机装起来。

我们需要进一步判断：

谁和谁必须一起考虑？谁决定谁？这个结构当初可能是按什么顺序长出来的？

这实际上是在尝试从一个静态的 Final CAD 中，恢复设计者当时的动态思考过程。

先分“耦合”和“独立”

第一个问题：

哪些东西必须一起设计？

如果 A 的变化会直接迫使 B 改变：

A→ B

那么两者之间存在较强耦合。

这种耦合可能来自：

  • 功能；
  • 尺寸；
  • 空间；
  • 受力；
  • 运动；
  • 线路。

例如两个模块如果共享：

  • 轴线；
  • 主承力结构；
  • 同一个包络；
  • 同一组运动空间；

往往很难真正完全独立设计。

反过来，如果两个模块之间可以被压缩成：

那么两边就可以获得更高的独立性。

因此看成熟开源时，可以主动寻找：

  • 哪些地方被设计者主动解耦？
  • 哪些尺寸明显被定义成接口？
  • 哪些结构必须整体推进？
  • 哪些模块可以单独拆下来换？

这不仅帮助我们理解现有机器，也会直接影响未来自己怎么拆项目。

再找“主要”和“次要”：谁决定谁？

第二个问题是：

谁是设计因果上的上游？

这里的“主要 / 次要”仍然不是价值评价。

所谓主要，更接近：

决定更多后续结构的变量

例如一个发射机构可能首先被：

决定。

然后：

  • 主体；
  • 支撑；
  • 防护；
  • 走线；
  • 外壳；

再围绕这些核心关系逐渐生长。

所以看开源的时候，不要只问：

“哪个零件最大？”

而应该问：

哪个决定了最多其他东西？

不要只看静态结果，要猜它当初怎么长出来

我们看到的通常都是：

Final CAD。

这很容易产生一种错觉：

这个结构好像天生就应该是这样。

当然不是。

设计者当初面对的也一定是一片空白。

真正值得学习的是：

这个模型可能是按照什么因果顺序生成的？

例如一个简单轴系：

真正需要恢复的，并不是：

“原作者 Fusion Timeline 第 17 个 Feature 是什么？”

而是：

设计依赖关系

也就是：

谁决定谁？

几何不是设计起点，而是设计决策的结果

例如看到一个轴承孔旁边有一个台阶。

如果只是复刻，新人可能记住：

“轴承孔旁边应该有台阶。”

但如果读设计：

于是你看到的不再是：

一个台阶。

而是：

一个轴向约束问题留下来的几何结果。

所以：

Geometry 不是设计对象本身，而是 Design Decisions 的结果

这应该是从“抄零件”走向“读设计”最重要的转变之一。

给关键尺寸“找爹”

这个方法很适合帮助新人训练设计因果。

看到一个关键尺寸时，不要只记：

“这里是 36 mm。”

问：

36 mm 是谁决定的？

可以粗略给尺寸标来源：

S — Standard

来自标准件。

例如：

  • 轴承外径；
  • 电机安装孔；
  • 同步带齿形。

F — Function

来自功能。

例如：

  • 行程；
  • 工作距离；
  • 抓取范围。

I — Interface

来自接口。

例如：

  • 和另外模块对接的位置。

M — Manufacturing

来自制造。

例如：

  • 刀具；
  • 板厚；
  • 最小加工特征。

A — Assembly

来自装配。

例如：

  • 工具空间；
  • 拆装路径；
  • 螺丝安装距离。

R — Rule / Envelope

来自规则或者包络。

例如：

  • 尺寸限制；
  • 运动空间。

E — Experience

来自经验或者测试。

例如：

  • 经过多轮实验确定的经验间隙。

于是一个很好的练习就是：

给每一个关键尺寸找爹。

如果一个关键尺寸完全找不到来源，可能意味着：

  • 它只是经验值；
  • 作者没有公开对应约束；
  • 或者你还没有真正理解。

特别关注那些“很可能被改过”的地方

最终版 CAD 最大的欺骗性之一是：

它把研发过程隐藏掉了。

真实结构可能经历了：

  • V0；
  • V1；
  • V2；
  • 多轮测试；
  • 多轮返工。

所以开源阅读时，可以特别观察：

  • 可调孔；
  • 垫片；
  • 快拆；
  • 易替换独立件；
  • 奇怪避让；
  • 后加加强筋；
  • 后加防护；
  • 多版本兼容接口；
  • 明显给后续修改留下的空间。

这些地方有时候恰恰保存了：

研发过程留下来的痕迹。

不要只问：

“它最后为什么长这样？”

也可以继续问：

它经历了什么，才不得不变成这样？

尤其要看风险、维护和可迭代性

成熟机器人设计考虑的并不只是：

“正常工况下怎么工作。”

还会考虑：

  • 什么最容易坏？
  • 坏了以后怎么换？
  • 哪些位置需要频繁调整？
  • 哪些结构依赖测试结果？
  • 哪些参数后续可能继续修改？

所以看开源时，非常值得观察：

  • 易损件是否局部化？
  • 维修是不是必须拆半台机器人？
  • 高频调整点是否容易接近？
  • 很可能改版的位置是否保留设计自由度？
  • 关键接口是否足够稳定？

这些东西可能没有一个漂亮公式，却会非常直接地体现：

作者有没有真正经历过研发和比赛。

05真正读懂了吗？——用条件变化测试理解

到了这里，一个非常自然的问题是：

我怎么知道自己是真的理解了，而不是“感觉自己理解了”？

最有效的方法之一，是主动改变条件。

不要只复刻。

给设计一个 Change Request。

例如：

Challenge A

轴承直径增加 20%。

Challenge B

电机长度增加 15 mm。

Challenge C

整个模块允许宽度减少 20%。

Challenge D

模块必须增加快拆。

Challenge E

原本的一体 CNC 必须改成板件组合。

Challenge F

负载提高一倍。

然后要求自己：

在保持核心功能成立的前提下重新设计。

这时候会非常快速地暴露：

你真正理解的是几何，还是设计逻辑。

如果只是记住：

“这里原来有一个孔。”

那么尺寸变化以后很容易完全不知道怎么继续。

但如果理解的是：

就会知道：

哪些关系必须保留，哪些几何可以重新生成。

因此：

条件改变以后还能不能合理变式

是判断自己是否真正读懂开源的一种非常有效的方法。

开源不是圣经

到了这里，也必须建立另一个观念：

开源不是绝对答案。

优秀开源非常有价值，因为它给我们提供了：

  • 已经走过的设计路线；
  • 成熟范式；
  • 真实工程经验；
  • 很多情况下甚至还有实战验证。

但现实中的开源也可能：

  • 没有公开最终比赛版本；
  • 隐藏关键尺寸；
  • 简化核心结构；
  • 上传的是中间测试版；
  • 因知识产权删掉部分内容；
  • 文档没有同步更新；
  • 本身就存在设计问题。

甚至：

“这台机器人最后赢了比赛。”

也并不意味着：

“它的每一个零件都是最优设计。”

一个系统可以在局部存在不完美的情况下仍然取得整体成功。

所以：

成功开源 = 高价值工程证据 ≠ 绝对真理

真正成熟的学习态度应该是：

尊重经过验证的设计，但保留自己的判断。

复现比迷信更可靠

如果某个关键设计真的非常重要，而你又准备把它迁移到自己的机器人上：

不要只因为：

“他们这样做过。”

就直接认为一定成立。

最好继续确认：

  • 工况是否一致？
  • 负载是否一致？
  • 速度是否一致？
  • 加工能力是否一致？
  • 材料是否一致？
  • 测试结果是否能够复现？

这也是“套公式”里最容易被忽略的一步：

检查适用条件。

06把“看过”变成自己的范式库

最后还有一个问题：

看完以后，留下什么？

如果一年以后，你的收获只是：

“我收藏过 47 台机器人 CAD。”

那价值其实非常有限。

真正有意义的是，把这些开源逐渐压缩成：

自己可以调用的设计范式。

不要记“某队 J0”，要记它解决问题的方式

例如最终真正应该留下的，可能不是：

“某队的 J0 是这样画的。”

而是：

远置驱动 + 留出中空通道 + 通过传动重新布置执行器。

后者才是可以迁移的知识。

同样：

“某队这里用了一个打印件。”

价值有限。

而：

“通过一个便宜、易替换的打印件，把高磨损失效集中到局部。”

就是可以迁移到其他项目里的范式。

所以：

实例 → 抽象范式 → 迁移到新问题

才是最终目标。

建立自己的 Pattern Card

以后看到一个真正值得记录的设计，可以不用保存一大篇笔记。

只记录几个问题。

Problem

它解决什么问题？

Pattern

采用什么结构范式？

Why

为什么这个范式适合当前场景？

Key Variables

哪些参数真正重要？

Constraints

成立需要什么条件？

Trade-offs

它付出了什么代价？

Risk

可能有哪些问题和失效模式？

Transfer

还能迁移到哪些其他问题？

随着积累越来越多，这些 Pattern Card 会逐渐变成：

自己的机械设计语言库。

一个实际可用的开源阅读 Checklist

如果以后拿到一套新的机械开源，不需要重新读完这篇文章。

只需要按照四个层级检查。

第一层｜看懂

  • 它是什么？
  • 它怎么工作？
  • 主要模块有哪些？
  • 有哪些自由度？

第二层｜拆解

  • 功能骨架是什么？
  • 驱动在哪里？
  • 传动是什么？
  • 运动副怎么实现？
  • 哪些模块耦合？
  • 谁是设计因果上的上游？

第三层｜解释

对关键结构反复问：

再进一步：

  • 关键尺寸来自哪里？
  • 哪些地方体现加工和装配限制？
  • 哪些结构可能是测试后改出来的？
  • 哪些地方在考虑维护和风险？

第四层｜迁移

主动改变一个条件：

  • 标准件；
  • 载荷；
  • 空间；
  • 接口；
  • 工艺。

然后问：

这个设计应该怎样重新生成？

最后再把真正值得留下的东西整理成 Pattern Card。

结从“看零件”到“读设计”

一个新人完成一套开源复刻以后：

原模型 327 个零件。 我的模型也是 327 个零件。

这本身并不能说明真正学会了多少。

更值得问的是：

把原文件关掉以后，你还能不能解释它为什么这样设计？

再进一步：

如果关键条件发生变化，你还能不能重新生成一个合理的方案？

开源学习真正希望发生的，是这样一次转换：

别人做出来的 Geometry → 我理解的 Design Logic → 我能够调用的 Design Pattern

前两篇《什么是好的机械设计？》讨论的是：

我们应该怎样评价一个设计。

这一篇讨论的是：

面对别人已经完成的结构，怎么把其中的设计知识重新读出来。

Requirement → Function → Constraint → Interface → Geometry
